## 2. ui + app 层能做什么 / 必须动 modbus-core 什么

**结论：没有任何一项在技术上“只能由 core 做”。** 面板需要的所有读写都可以经现有 `SessionManager.execute(ModbusRequest)`（已被工作台使用）完成。ui-plan 把“换算 / 采集 / 缓冲”放进 core（UI-3a），是**架构偏好**（可单测、可复用、与 Android 无关），不是能力限制。所以有两条路，需要老板选：

- **路线 A（推荐，在“core 不动”约束内）**：在 app 模块新建纯 Kotlin（不依赖 Android）的包 `application/panel/`（`ValueCodec`、`PollScheduler`、`PointStore`、`CurveBuffer`、`ProjectRepository`），写成“可原样搬进 core”的形状（无 Android 类型、可 JVM 单测）。以后老板放开 core 时整包移动。代价：与 ui-plan 的目录约定不一致；以后要搬一次。
- **路线 B**：老板放开 core，**只新增文件**（`core/conversion/ValueCodec`、`core/monitor/*`），不改协议和已有类。工作量与 A 相同，少一次搬迁，但违背当前“core 不动”。

具体到各块：

| 能力 | ui+app 层 | 是否需要 core | 说明 |
|---|---|---|---|
| 工程/面板/组件/点位配置存储 | ✔ 做得了 | 否 | `filesDir/projects/<id>.json`，临时文件 + rename 原子写；DataStore 不适合（大结构）。序列化：`org.json`（零依赖）或加 kotlinx-serialization 插件（改 app 的 build.gradle，是依赖变更，需确认） |
| 数据换算 ValueCodec（U16/S16/U32/S32/F32/U64/S64/F64/BCD/ASCII，字序，缩放，位） | ✔ | 否（`DataConversion` 是空的，spec 归 core M4） | 纯函数，JVM 单测；64 位不经 Double |
| 采集 PollScheduler（相邻地址合并、周期、过期） | ✔ | 否；**但有一个局限** | `MasterEngine.execute` 是 `Mutex`（FIFO 公平），“手动请求优先”做不到，只能做到“和轮询交错、最多等一次读”；若老板要严格优先 / 取消正在排队的轮询，才需要改 core |
| PointStore（最新值、质量、时间） | ✔ | 否 | 内存 StateFlow |
| CurveBuffer（环形缓冲、min/max 降采样、缺测段） | ✔ | 否 | 纯算法 |
| 样本历史落盘 | ✔（文件/Room） | 否 | ui-plan 说“这次不落库”，Room 留 UI-6 |
| 后台持续采集（切到别的 App 仍采） | ✔（前台 Service，manifest + 通知） | 否 | 需要用户确认是否要后台采集；USB 权限/断线处理已在 SessionManager |
| 面板网格 / 8 种组件 / 质量态 | ✔ | 否 | 纯 Compose |
| 编辑模式（拖动排序、改尺寸、删除） | ✔ | 否 | 拖动用 `pointerInput` 自己写（项目已有自写手势习惯），或网格库（不引入） |
| 添加向导 3 步 + 预览 | ✔ | 否 | nav-graph 作用域 VM |
| 曲线 Canvas、游标、双 Y 轴 | ✔ | 否 | 不引第三方图表库（ui-plan 约定） |
| 写入类组件 | ✔ | 否 | 复用工作台的 ConfirmSheet/WritePlanner（目前在 ui 层，过渡） |
| 会话条“实际 1012 ms” | ✔（调度器自己量） | 否 | |
| “位写入先读后写” | ✔ | 否 | 非原子，只能提示 |
| 从站面板 / 模拟规则（b5-4/5） | ✘ | **是**（ValueSimulator，UI-4） | 不在本评估范围，保持“依赖 core” |
| 值来源 `RegisterChange.source`（从站“谁改的”） | ✘ | **是** | 与面板主站部分无关 |

## 4. 需要老板拍板
1. 路线 A（app 层 `application/panel/`，core 不动）还是路线 B（放开 core 仅新增文件）？
2. 序列化库：`org.json`（零依赖，写得啰嗦）还是 kotlinx-serialization（要改 app 构建依赖）？
3. 轮询冲突策略：接受“和手动请求交错，最多等一次读”，还是要严格优先（需要改 core 的 `MasterEngine`）？
4. 是否要后台持续采集（前台服务 + 常驻通知）？默认建议 **不要**，先做前台采集。
5. 样本历史：只内存（ui-plan 默认）还是现在就落盘？

## 5. 未验证 / 风险
- 本评估只读了代码与设计稿，没有写任何原型；行数/天数是经验估计。
- `MasterEngine` 的 `Mutex` 在大量点位时对手动请求的延迟没有实测。
- 稿面是 26 个画面里最重的一块，且曲线重绘性能、拖动手感必须真机验证（我不操作模拟器）。
